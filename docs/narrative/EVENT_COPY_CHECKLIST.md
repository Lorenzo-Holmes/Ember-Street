# Ember Street — Event Copy Checklist

本文件用于第二轮事件语料清理。目标不是把规则藏起来，而是让玩家先看到“发生了什么”，再看到“这个决定会花什么、赌什么”。

## 1. 三层顺序

每个事件都按以下顺序组织：

1. **现场**：能看见、听见、闻到或从人物口中得知的事实。
2. **动作**：玩家真正让谁去做什么，或决定不做什么。
3. **硬信息**：成本、2D6 修正、失踪/死亡、居民伤亡等必须明确的信息。

正文和 choice detail 不承担完整规则说明；规则由标签和决策提示层补足。

## 2. Choice detail 应该写什么

优先写：

- 人要走到哪里；
- 要搬、关、点、拆、守、等什么；
- 谁会暴露在危险里；
- 哪一块街区会因此变暗、变空、变脆弱；
- 谁会记住这件事。

例如：

- 不写“用电力换一次稳定确认”，写“把外围灯全打亮，让围栏外的人无处躲在黑暗里”。
- 不写“接受噪音带来的风险”，写“今晚不出去赶，叫声会继续沿街传出去”。
- 不写“医疗能力会受影响”，写“只保呼吸机和手术灯，其他床位今晚只能摸黑处理”。
- 不写“没有立即代价”，写“今晚先不谈，那个空位还会留在主灯旁”。

## 3. 主正文禁用表达

玩家可见的事件正文、地点描述和 choice detail 尽量避免：

- 解锁 / 触发 / 事件池 / 后续事件
- 稳定方案 / 稳定确认 / 直接处理
- 长期效果 / 隐藏任务 / 推荐入口
- 没有奖励 / 无物资收益（可放硬信息标签，不放故事正文）
- 接受风险 / 承担风险 / 风险更高（正文应改写成具体危险）
- 玩家 / 用户 / 系统

## 4. 允许保留的硬信息

以下信息不得为了气氛而模糊：

- `口粮 -N / 药品 -N / 电力 -N / 材料 -N / 零件 -N`
- `2D6 ±N`
- `需要 2 人`
- `严重失败可能失踪/死亡`
- `居民伤亡风险 / 居民必减员`
- `第二次搜救失败会确认死亡`

这些信息属于第二层 UI，不需要伪装成世界内对白。

## 5. 夜间事件检查

逐条检查：

- 是否能从正文想象出一个具体镜头；
- 三个选择是否对应三个可区分的真实动作；
- resource 选择是否写成“拿什么去解决现场问题”，而不是“稳定方案”；
- consequence 选择是否写清楚“不做/撤退/关闭”后现场会变成什么样；
- 死亡、失踪、居民伤亡仍由风险标签明确提示。

## 6. 探索地点检查

地点卡不写“前期缓冲”“高风险收益”“DAY29 准备”一类策划语言。

地点 features 应尽量是人物会写在地图边上的短词，例如：

- “后仓可能有吃的”
- “地下室没确认过”
- “楼顶有人点过灯”
- “金属声会传很远”
- “隧道里没有第二条退路”
- “北仓库靠近尸群迁移方向”

## 7. 截图审计节点

完成语料修改后固定检查：

- DAY 1：玩家是否能理解这条街从哪里开始；
- DAY 7：规则第一次开始形成时是否仍像人在做决定；
- DAY 14：设施、居民和广播增多后是否出现大量系统术语；
- DAY 21：撤离路线与长期成果是否仍以世界事实呈现；
- DAY 29：终局硬信息是否清楚，但没有变成纯战斗面板。

UI Smoke 中应持续保留这些里程碑截图。
